# App audit — November 2026

Run against `main` at `76648f7`, read-only: no rows were written, no live control
was clicked. Numbers in the shop-data sections are from the production Supabase
project as of 2026-11-06.

Three passes: correctness (code + database), design, and a competitive read.

---

## 1. Correctness

Nothing here is on fire. The money math is provably in sync, the customer-facing
surface does not leak, and the payment cache matches the ledger exactly. What is
below is four real gaps, all latent, plus one class-level observation.

### 1.1 The customer report includes soft-deleted vehicles — LOW, latent

`app/report/page.tsx:234`

```ts
const { data: vs } = await supabase
  .from('vehicles')
  .select('*')
  .eq('customer_id', customerId)     // no .is('deleted_at', null)
```

The jobs query sixteen lines below it *does* filter (`.is('deleted_at', null)`),
which is the tell that this one is an oversight rather than a decision. On
`/report?customer=…` a vehicle that was deleted — usually because it was entered
by mistake — comes back, and its live jobs print on the service history.

**Not reachable today.** There is 1 soft-deleted vehicle and 0 live jobs hanging
off it, so nothing currently prints that shouldn't. The page is also inside
`AuthGate`, so only the owner can generate it, and the output is a document that
gets reviewed before it goes anywhere.

**Fix:** add `.is('deleted_at', null)` to match the sibling query. One line.

### 1.2 Payment-cache repair has no backstop — MEDIUM as a risk, no drift today

`syncJobPayment()` re-derives `jobs.payment_status` and `jobs.amount_paid_cents`
from the payments ledger. It is called in at least six places, every one of them
like this:

```ts
try {
  await syncJobPayment(id)
} catch {}
```

Swallowing it is defensible — a cache refresh should not block the owner mid-job.
The problem is what is *not* there:

- **No server-side backstop.** The only triggers on `payments` are
  `payments_updated_at`. Nothing in the database re-derives the cache, so this
  client-side call is the only thing keeping it true.
- **No retry and no marker.** If it fails, nothing records that the job needs
  re-syncing and nothing tells the owner.

Those cached columns feed `collectedForJob()`, the dashboard cash tiles, the
Reports receivables and the paid badge. A silent failure would show the wrong
money and look exactly like the right money.

**Measured:** every live job's cache matches its ledger to the cent right now —
20 jobs, 0 discrepancies. This is a resilience gap, not an active bug.

**Fix, cheapest first:** (a) a trigger on `payments` that maintains the cache
server-side, which removes the failure mode entirely; or (b) log the failure and
show it in Settings as "N jobs need a payment re-sync" with a button.

### 1.3 `is_adjustment` is read everywhere and written nowhere — LOW, dead code

The column is honoured in ten places — `lib/billing.ts:71`,
`lib/authorization.ts:199`, `lib/invoice-refresh.ts:80`, `lib/conditions.ts:49`,
the invoice page, `BillingCheck`, the job page — all of them excluding flagged
lines from invoices and authorization totals.

Nothing in the app ever sets it. No default of `true`, no trigger, no migration
backfill: **0 of 59 part lines are flagged.**

So the guard has never once fired. Today's credit lines (a `DISCOUNT`, a
`Core Charge Return`, a warranty return) flow onto invoices as ordinary negative
lines, which appears to be the behaviour that is actually wanted. The hazard is
that a whole exclusion path exists, is wired into the billing and authorization
maths, and has never executed — so the day anything sets the flag, the behaviour
is untested.

**Fix:** either build the UI that sets it, or delete the column and the ten
branches that read it. Leaving it half-wired is the worst of the three.

### 1.4 Supabase hardening — LOW, two of them are dashboard toggles

From Supabase's own advisors plus a look at the definitions:

| Item | Reality |
| --- | --- |
| Leaked-password protection is **off** | One checkbox. Worth turning on for a single-account app that is the shop's books. |
| 7 functions with mutable `search_path` | `is_owner`, `set_updated_at`, `apply_quote_to_job`, `shop_today`, `part_lines_clear_awaiting_cost`, `snapshot_pre_tax_cents`, `quote_lines_frozen_once_applied`. |
| `is_owner()` specifically | Flagged, but it is `SECURITY INVOKER` (no escalation) and its body fully qualifies `auth.jwt()`, so there is nothing unqualified to shadow. Practical exposure here is nil; set `search_path` anyway as defence in depth. |
| 6 `SECURITY DEFINER` functions callable by `anon` | Intentional — that is the whole public-link feature. Verified field-by-field below. |

**One thing worth checking that the advisors cannot see:** access is pinned to
`auth.jwt() ->> 'email' = 'jfisher907@gmail.com'`. There is exactly one confirmed
user and no signup UI, but if email signups are still enabled on the Auth
settings, the security model leans on nobody being able to confirm that address.
Disabling signups outright costs nothing — there is no signup flow to break.

### 1.5 27 empty `catch {}` blocks — observation

Most are deliberate and harmless (best-effort cache nudges). They are called out
as a class because the pattern makes 1.2 invisible: when the failure mode is
"nothing happens", there is no way to distinguish working from quietly broken.
Worth a convention — swallow, but count it somewhere the owner can see.

## 2. What was checked and found clean

Stated with the evidence, because a clean result is only worth the strength of
the check behind it.

### Money math is provably in sync

`lib/calc.ts` `computeTotals()` is the optimistic-UI mirror of the `job_totals`
view, and AGENTS.md calls keeping them identical a standing requirement. The
mirror was re-expressed in SQL and diffed against the view across **all 20 jobs
and all six fields** — labor, parts cost, parts charged, total charged, profit,
included tax:

```
jobs_compared: 20   labor_diffs: 0   parts_cost_diffs: 0   parts_charged_diffs: 0
total_diffs: 0      profit_diffs: 0  inc_tax_diffs: 0
```

The comparison was then re-run with a deliberate 1-cent error injected, and lit
up on 20 of 20 — so the zero means agreement, not a broken test.

One near-miss worth recording: `line_charge_total_cents` is nullable, and the
view's `sum()` ignores NULLs while the mirror falls back to cost
(`?? l.line_total_cents`) — which would have been a real divergence. It is not,
because the column is `GENERATED ALWAYS AS round(qty * COALESCE(unit_charge_cents,
unit_cost_cents))`. The fallback lives in the generated column, so both sides
agree by construction.

### The public token surface does not leak

Every field the five anon-callable RPCs actually hand out was enumerated by
calling them `set role anon` and flattening the JSON, rather than by reading the
SQL. Top level and nested — `lines[]`, `authorizations[]`, `business`:

- **No** cost, profit, margin, markup, private note or internal field anywhere.
- `get_public_inspection` redacts the repair-estimate ranges **server-side**:
  `'cost_low_cents', case when i.show_costs then it.cost_low_cents end`. The
  "turn off before it goes to a seller or bank" toggle actually withholds the
  numbers rather than just hiding them in the client.
- `get_shared_photos` requires **both** the per-photo flag and a token that
  resolves to that job, filters soft-deleted quotes and void invoices, and the
  bucket stays private with URLs signed for 1 hour.
- Write-capable RPCs (`respond_public_quote`, `record_card_payment`,
  `submit_service_request`, `book_stripe_fee`, `record_deposit_payment`) are
  **`service_role` only** — not callable from a browser.
- `anon` has no direct table access (confirmed: `permission denied for table
  inspections`).
- Every public read gates on state as well as token: invoice not void,
  inspection `status = 'final'` and `link_revoked_at is null`.

Note on naming: invoice and quote `lines[].line_total_cents` is the **charge**
total, not cost (`lib/billing.ts:149` maps `line_charge_total_cents` into it).
The value is correct; the name invites a future mistake.

### Other checks, all clean

| Check | Result |
| --- | --- |
| Invoice snapshots internally consistent (`total = labor + parts + tax`) | 0 mismatches |
| Invoice immutability | Enforced in the database by the `invoices_paper_frozen` trigger, not just by convention |
| Payment cache vs ledger | 20 jobs, 0 discrepancies |
| Orphan jobs / part lines | 0 / 0 |
| Negative part lines | 6, all legitimate credits (warranty return, core returns, a discount) |
| Jobs marked paid with no evidence | 0 |
| `ANTHROPIC_API_KEY` | Server-only, never returned, never `NEXT_PUBLIC_`. Only the Supabase URL and anon key are public, which is correct under RLS |
| API route auth | 6 routes use `clientForRequest()` (bearer → RLS-scoped client, 401 on failure). The rest are public by design and gated another way: Stripe signature on the webhook, token on the photo and quote-response routes |
| Auth users | Exactly 1, confirmed, email provider |

## 3. Design

### 3.1 Four segmented controls were missed in the Liquid Glass pass

The glass work converted four rows to `.seg-track`, found by searching for the
`flex-1` / grid idiom. It missed the rows that use the other idiom — `btn btn-sm`
with `btn-primary` on the active one — so these are still loose pills where the
house rule says segmented control:

| Where | Options |
| --- | --- |
| `app/(app)/followups/page.tsx:207` | Open / Booked / Everything (3) |
| `app/(app)/hangar/history/page.tsx:119,126` | Sessions / Unavailability (2) |
| `app/(app)/taxes/page.tsx:506,510` | Cash / Accrual (2) |
| `app/(app)/inspections/[id]/page.tsx:339` | Driven / Not driven (2) |

Correctly **not** segments, for the record: the hangar date presets (6 options,
over the 2–4 rule), the JobForm template picker (variable length), and the
single on/off toggles.

Borderline: the inspection **verdict** (3 options, mutually exclusive) — but the
labels are "No major concerns found", "Repairs to price in", "Major concerns
found". Those will not fit three-across at 375. Either leave them as pills or
shorten the labels to fit a track.

### 3.2 The customer phone link is invalid HTML, and it wraps — MEDIUM

Two problems in one element, `app/(app)/customers/page.tsx:193`.

**It is an `<a>` inside an `<a>`.** The tappable phone link sits inside the card
`Link`, which renders an anchor. React logs it on every load:

```
<a> cannot contain a nested <a>.
```

Measured in the live DOM: **14 nested anchors on `/customers`**, one per customer
with a number. This matters beyond tidiness — an HTML parser cannot nest anchors
and will split the outer one, so the server-rendered markup and the client DOM
disagree, which is a hydration mismatch. The `e.stopPropagation()` keeps React's
synthetic events behaving; the underlying DOM is still invalid, and keyboard and
screen-reader handling of nested anchors is undefined.

**And it wraps mid-number.** No `white-space: nowrap`, so in a flex row with the
customer and vehicle name, Airlift Northwest's number renders across three lines
as `208-` / `356-` / `2471`. Several others break across two. This is the page
whose whole purpose is finding a number fast with one thumb.

**Fix, one change for both:** take the phone out of the card link. Make the row a
plain container with the name as the `Link` and the phone as a sibling `<a>`,
then add `white-space: nowrap` and `font-variant-numeric: tabular-nums`. That
removes the nesting, the hydration risk and the wrapping together.

The rest of `/customers` is clean: no unlabelled inputs, no images without alt,
no touch target under 44px across 53 of them.

### 3.3 The jobs filter row is too tight at 375

Status select and two date inputs sit three-across at **98px each**. The select
shows "All statu" and both dates clip to "mm/dd". Nothing reports overflow —
`scrollWidth` is 96 against a 98px box — because a `<select>` truncates in the
native widget and a date input clips its own segmented UI, so only looking at it
catches this.

Pre-existing, not caused by the glass pass: `.input` and `.select` padding is
unchanged at `9px 12px`; only the corner radius moved.

**Fix:** at phone width give the status select its own row and put the two dates
side by side beneath it. A date field needs ~115px to show `mm/dd/yyyy` plus the
picker icon.

### 3.4 Inline links on Follow-ups are 14–30px tall

Six targets under the house 44px minimum on `/followups`, all of them the inline
customer and vehicle links inside the flagged-work cards: the customer name at
**14px** tall, the vehicle at **30px**.

These are links inside running text, so the 44px rule is not a straight read —
making every inline link 44px would wreck the paragraph. But the codebase has
already solved this exact case elsewhere: `.cal-waiting-item` is
`min-height: 44px; display: inline-flex` precisely so the calendar's inline job
links are thumbable. Applying the same treatment here would make it consistent.

Other pages measured clean on target size: `/jobs` 0 under 44px, `/customers` 0
of 53, `/expenses` 1 of 35.

### 3.5 Smaller notes

- Fetch-by-id reads on soft-deleted tables (12 sites) do not filter `deleted_at`.
  Mostly correct — you arrived from a list that filtered, and Settings has the
  restore flow — but a stale bookmark to a deleted job opens it as if it were
  live, with no indication it is deleted. A "this was deleted" banner on
  by-id loads would close the loop cheaply.
- The Taxes page leads with one very long, text-dense card. It reads well and
  the content is genuinely load-bearing, but it is roughly two phone screens
  before the first number. Worth considering whether the figures come first and
  the explanation sits under a disclosure.

## 4. Competitive read

### What this app is actually competing with

Entry pricing for cloud shop-management platforms, from several 2026 comparisons
(all vendor or affiliate sources, so treat as directional and confirm before
acting):

| Product | Entry / month | Notes |
| --- | --- | --- |
| Tekmetric Start | ~$199 | Per shop, unlimited users, no contract |
| AutoLeap Essentials | ~$199 | No published price or self-serve trial |
| Shopmonkey Basic | ~$239 | 3 users, +$20/user after; ~$500 migration fee reported |
| Shop-Ware Startup | ~$279 | Per shop |
| Budget / flat-rate tier | ~$40–180 | GreaseGoose ~$40, Eligant ~$39, autoGMS ~$219 |

Two-way texting sits on higher tiers for Tekmetric (~$439) and AutoLeap (~$349);
Shopmonkey includes it from entry. Entry plans at Shopmonkey and AutoLeap omit
inventory.

### The number that settles it

Shop volume from the live data: **4.2 jobs/month**, 12 done, $599 average repair
order, 15 customers, 17 vehicles, 12 live invoices, 9 quotes.

The industry's own buying guidance puts the point where this software pays for
itself at **above ~60 repair orders a month**, and explicitly names buying
enterprise tiers below that as the most common small-shop mistake.

At 4.2 ROs/month, Tekmetric Start would cost about **$47 per repair order** —
roughly **8% of a $599 ticket, before parts cost**. Shopmonkey Basic would be
about $57. There is no version of that which makes sense. The bespoke app's
marginal cost is a Vercel project, a Supabase project and an Anthropic key.

So the right comparison is not "is this as good as Tekmetric" — it is "does this
do the jobs a one-person shop actually needs, at a cost that is not absurd".
Mostly yes, with real gaps.

### Where the commercial products are genuinely ahead

These are not polish items; they are data assets a bespoke app cannot cheaply
replicate.

1. **Labor guides.** MOTOR/Mitchell book times by VIN, one click into the
   estimate. Here, `labor_hours` is typed by hand. This is the single biggest
   functional gap — book time is the denominator of the whole book-vs-actual
   feature, and right now it is a guess.
2. **Parts catalogue and ordering in the estimate.** PartsTech, Nexpart, NAPA,
   WorldPac — search, price and order without leaving the job. Here there is an
   O'Reilly PO field and receipt scanning, which is a reasonable substitute for
   ordering but not for live pricing and availability.
3. **Accounting sync.** Native QuickBooks/Xero. Deliberately skipped here, and
   the reasoning in the roadmap holds — this app *has* the ledger, both P&L
   bases, sales tax and A/R — but it will matter the day a tax preparer asks.
4. **Inventory.** Not modelled at all. Probably correct at this size.
5. **Two-way texting** as a first-class channel with threads and templates.

### Where this app is ahead, and not trivially

1. **Juneau sales tax, correctly.** 5% applied *on top* per CBJ Procedure 130,
   the rule that a seller who billed no tax may not back it out, the
   `included_tax_cents` booking for untaxed invoices, the filing calendar and the
   record of what was filed. Generic platforms handle "a tax rate", not a
   specific municipality's procedure. This is compliance work nobody else does
   for him.
2. **Alaska Auto Repair Act handling.** Zero tolerance over an approved estimate,
   compared on totals, with the authorization cap enforced in the billing maths.
   Commercial products have estimate approval; they do not encode AS 45.45.
3. **The core deposit lifecycle.** Four states, the five-day credit chase, the
   30-day return window, and the rule that the customer never pays a core unless
   the store denies it. This is usually a sticky note.
4. **Book time vs actual, already built.** Mitchell 1 sells this as Time Manager;
   it is in here with a clock that follows you across screens.
5. **Pre-buy inspections and the aviation side.** Transient-jet AOG work, the
   hangar board and ALNW usage billing. No automotive platform touches this.
6. **Profit is structurally absent from customer paper**, enforced at the
   database boundary rather than by remembering.
7. **Phone-first for one pair of greasy hands**, rather than a desktop service
   writer's console squeezed onto a phone.

### Honest risks

- **Bus factor of one.** No vendor, no support line, no one else who knows the
  schema. The documentation in the repo is unusually good, which is the right
  mitigation, but it is still one person.
- **Book time by hand** is the gap most likely to cost real money — undercharging
  labour is invisible in a way that undercharging parts is not. A cheap partial
  fix: record actual hours per job type over time and let the app suggest a book
  time from the shop's own history. The data is already being collected.
- **Stripe is still on test keys.** Card checkout cannot take a real payment
  until live keys are added.

### What I would not change

Nothing in the competitive read argues for buying a platform at this volume, and
nothing argues for chasing feature parity. The two things worth stealing are a
labor-time source and live parts pricing — and the first can be approximated
from data the app already has.

## 5. Suggested order

1. `report?customer=` soft-delete filter — one line, closes a real if latent hole.
2. Disable Supabase signups; turn on leaked-password protection — two toggles.
3. The customer phone link — invalid nested anchor plus the wrapping, one fix.
4. The jobs filter row at 375 — visible every day.
5. The four missed segmented controls — finishes the glass pass properly.
6. Decide `is_adjustment`: build it or delete it.
7. A payments trigger to maintain the job payment cache server-side.
8. Longer term: book time suggested from the shop's own history.
